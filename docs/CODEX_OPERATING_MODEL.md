# CODEX_OPERATING_MODEL｜かっしーは監督、Codexは実行責任者
版 2.0 / 開発の自律性と外部公開の承認を分ける

## 1. 役割と成果物
| 役割 | 担当 | 具体的成果物 |
|---|---|---|
| 監督 | かっしー | 操作感/画質の可否、例外・費用・公開の決定 |
| 実装リード | Codexの主担当1つ | 調査、環境準備、設計、実装、テスト、修正、差分、継続状態 |
| 品質レビュー | 利用可能なら別コンテキストのレビュー担当1つ | 要求・差分・試験証拠からの指摘と再検証 |

多数の専門家ロールを演じるだけの会話は作らない。通常のUI・データ・画像処理の判断は主担当が引き受け、監督にライブラリ選定を丸投げしない。レビュー担当は同じファイルを同時編集しない。別担当を実行できなければ自己レビューと正確に記録し、独立レビュー済みとしない。

## 2. 継続の原則
M0の環境監査だけ、または撮影1枚のPoCだけで仕事を終えない。PLANSのマイルストーンを進め、失敗を修正し、EVALSとSTATEを更新する。内部の技術ゲート合格なら次へ進み、毎回「次を実装してよいですか」と聞かない。
実機や認証待ちはその検査をNEEDS_HUMAN_TEST/BLOCKEDにし、依存しない安全な実装・テストを続ける。ただし未合格の共有/保存/画質を完成扱いして公開しない。
Codexの実行時間・利用枠・権限には制限がある。1回の指示で無制限に常駐することは保証しない。セッション終了前に実行中ジョブ、ブランチ、コミット、次の作業をSTATEへ残し、再開は「STATEから続けて」で済むようにする。

## 3. 自律で進めること（許可された作業領域内）
仕様の整合性確認、公式資料の必要部分の確認、低リスクな設計修正、指定ワークスペース内の実装、合成データの生成、テスト・ビルド・静的解析、ローカルの修正・検証、変更記録。
ロックされた依存のインストールやブラウザー試験資源の取得は、初回にネットワーク範囲と保存先を整理して承認を得た後、その範囲でまとめて行う。サンドボックスの境界を回避しない。
指定リポジトリへの開発ブランチpushとDraft PRは、その所有者/可視性/自動配信の影響が確認され、外部書込みの許可を得ている場合のみ行う。

## 4. 監督に返すこと
- 課金、契約、新しい外部サービスへの登録/認証、追加クレジット購入。
- 検証公開の初回許可、本番公開/マージ、公開先や対象者の変更。
- 実データの削除/上書き/外部送信、プライバシーや権利判断。
- 無料/iPhone/直接メール共有/画質など中核条件を満たせない場合の縮小判断。
- 実機でしか確認できない撮影/添付/保存の最小操作。

認証・本人確認・端末のカメラ操作・OS共有画面の最終送信は、本人または協力者の操作が残る。認証は本人が行い、チャットにパスワードやトークンを貼らせない。端末購入・Mac購入を初版の前提にしない。

## 5. 判断カード
必要なときだけ `templates/DIRECTOR_REPORT.md` を使う。見てもらう画面または試験成果、判定、影響、推奨案、変更/復旧範囲を示し、1回に重要な判断は1つ。
悪い例: 「IndexedDBかOPFSどちらにしますか？」
よい例: 「現行方式は10枚PDFで合格、20枚でiPhoneの処理が停止しました。画質を守り10枚ずつ分ける案を推奨します。20枚一括を初版必須にしますか？」

## 6. 環境監査とセットアップ
OS、Codexのローカル/Cloud、Gitと作業tree、既存のルート指示、Node/package manager、ブラウザー試験機能、ネットワーク、ログイン済みコネクタを読む。未確認のowner/repoや過去の別案件を作業対象にしない。
Nodeは導入時点のサポートされたLTSとViteの必要条件を照合し、パッケージロックを1種類だけ使う。Windows/WSL/Macを無秩序に二重設定しない。PWAのためAndroid Studio・JDK・Xcodeは標準環境の必須条件ではない。[W21]
既存コードがある場合は全消去ではなく影響調査。v1のAndroidコードが存在するなら、資料しかなかったと決めつけず、別ブランチに移行案と必要な保存データ移行を作る。

M0で整備する開発コマンド（本資料の時点では未実装）:
`npm ci` / `npm run dev` / `npm run typecheck` / `npm run lint` / `npm run test` / `npm run test:e2e` / `npm run build` / `npm run preview`。
実際にpackage.jsonへ定義した後でコマンドを試す。存在しないスクリプトを実行済みと報告しない。E2E用WebKitと実iPhoneの結果は別列に記録。

## 7. 安全と低負担を両立する設定
config例は `config/codex-config.example.toml`。workspace-write / on-requestを基本にし、必要なセットアップ許可は最初に集約する。danger-full-access、--yolo、無条件の権限昇格を「楽にする方法」としない。[O06]
設定例を作っただけで適用済みとは言わない。既存ユーザー設定を上書きしない。Cloud CodexではローカルTOMLの設定をそのまま使えると仮定せず、環境側のネットワーク/セットアップへ翻訳する。
ブラウザー操作・コネクタ・MCPの権限はサンドボックス設定と別の場合がある。ファイル規則だけで外部送信を防げると考えない。初回公開は明示承認を要する。

## 8. Dラボから取り込む内容
DラボのPLANS.md紹介（2025-11-25）、AGENTS/Skills/レビュー紹介（2026-02-26）、作業環境整理の紹介（2026-06-09）を検索抜粋から取得。最新ブログ一覧は2026-09-30の記事まで確認。全文視聴/全記事精読とは扱わない。[D01-D04]
採用は、自己完結した実行計画、進捗/判断の記録、再利用できる作業規則、実装とは切り分けたレビュー。並列エージェントの大量起動、非公式モデル切替、宣伝上の費用削減率は採用しない。
OpenAI公式の現行案内と照合し、短いAGENTS、必要な範囲だけ読むSkills、成果で判定できるマイルストーンへ翻案した。Dラボがこのスキャナー技術構成を保証したわけではない。[O02-O05, O07]

## 9. モデルとトークン
2026-10-02の公式資料では、利用可能な場合の複雑なコーディング候補にGPT-6.1 Sol、範囲の明確な反復作業にLunaの案内がある。アカウント・クライアントの実際の選択肢で確認し、利用できないモデルを前提にしない。[O01]
本案件では主担当を対応モデルの通常の推論量で継続し、保存競合・画像座標・更新移行などの難所だけ推論量を上げる。軽い作業のたびにかっしーにモデル切替を要求しない。複数モデル自動ルーティングや別の有料APIを新設しない。
固定した狭い修正・文言の見直しをまとめて軽量モデルへ任せる場合だけ切り替える。設定が使えなければ同じモデルのまま進める。Max/Ultra常用や常時多数並列で無料/省コストの目的を崩さない。
AGENTSは不変条件と参照先に限定する。全設計書の毎回再読込み・無関係な全テスト再実行・同じ調査の繰返しを避ける。ただし保存/共有/更新の回帰検査は省かない。節約効果は測定前に数値化しない。[O07]

## 10. セッション終了時の報告
変更と動く経路、実行したテストの証拠、実機未実施、残るリスク、次に実行する作業、監督判断の有無だけを簡潔に返す。長い内部思考の説明は不要。
Dラボ接続がCodexに引き継がれるとは仮定しない。取得要点はSOURCES/STUDYへ保存済みなので、Codexはそれを使って作業できる。追加知見の取得ができない場合も、既確認の設計と公式情報で進める。
