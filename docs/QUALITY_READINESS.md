# 実機・使いやすさの検証計画

2026-10-06 / readiness review / 基準コミット43b916d / 対象buildは配布台帳で固定する。

## 結論と根拠

Androidでの小規模実験準備は **GO WITH CONDITIONS**。実機試験はHTTPS検証URLと端末情報を確定後に開始する。一般提供は **NO-GO**。iPhone未検証、実機の画質・共有・復元・更新が未合格のため。Androidのみ利用可能という本人回答は、初版で両OS対応する要求R09を撤回しない。

根拠: PROJECT_BIBLE、EVALS、PLANS、docs/DEVICE_TEST_GUIDE、evidence/browser-results.json。AIによる自己レビューであり、複数人の合意や独立レビューではない。

Dラボ「[不自由発想術 #3 収束の技法](https://daigovideolab.jp/play/fuuGdAlN1phNHjEv1gig?t=1650)」の、致命的な失敗仮説を先に洗い出し低コストで小さく検証する考え方を参考にする。以下の人数・閾値は本プロジェクトの暫定案であり、Dラボが定めた品質基準や統計的保証ではない。

## 順序とゲート

1. **事前検査（Codex）**: 合成テスト、主要E2E、320/360/390/412pxと横向き、ラベル・操作到達性、配布物の内容確認。不具合は修正して該当検査を再実行する。
2. **Android本人確認（15〜20分目安）**: Chromeで撮影1枚→四隅→白黒/カラー→保存→PDF→メールへ添付→本人が自己宛に送信→受信PDF。迷った場所と原本比較を記録。機種/OS/Chrome/メール/buildを残す。
3. **耐久・保存確認（別枠）**: ホーム画面版、カメラ/共有画面で30秒待って復帰、アプリ再起動、機内モード、1/5/10枚PDF、別保存領域へ復元、再取込、更新前後の20原本保持。10枚PDF30秒、受取後保存5秒はEVALS既存の暫定目標。OS終了や勝手な画質低下0。
4. **初見の協力者3人（暫定案）**: 普段紙を送る人。1人ずつ、T1〜T3。観察者は先にボタンを教えない。60秒以上進めない場合は介助してよいが「自力完了」には数えない。時間は終了まで測り、途中の考え・迷いを短く記録。録画は本人同意時のみ、個人文書は不要。
5. **iPhone確認**: Safari/ホーム画面版でD01/H01/B03/U01/U02。端末を確保するまでNEEDS_HUMAN_TEST。Android合格を転用しない。
6. **提供判定**: 必須EVALSの証拠が揃う、P0/P1=0、主要作業を止めるP2=0。軽微な既知制限は説明・回避手順・修正予定を明示。本人が限定提供を承認してから配布し、3日間の利用で同じ指標を確認（期間も暫定案）。改善率は従来手順を同条件で測れた場合のみ算出する。

### 初見者へ読み上げる課題（操作名を含めない）

- T1: 「この架空の紙1枚を、今日の日付の読みやすいPDFにして、自分のメールに添付できるところまで進めてください」。本人テストだけ受信確認も行う。
- T2: 「3枚のうち2枚目と1枚目を、この順番で『提出テスト』というPDFにしてください」。選択外の混入0、順序一致。
- T3: 「明日も続けられる状態にしてください。さらに、端末が使えなくなったときに備えて保存し、別の試験用保存領域で戻してください」。アプリ内と端末外を区別できるか観察。

課題後: 「一番迷った箇所」「そう思った理由」「次は1人でできそうか（1〜7）」を聞く。平均満足度だけで致命的不具合を相殺しない。

## 不具合と再検査

P0/P1はEVALSの定義を維持し直ちに試験配布を止める。P2=主要操作を自力で終えられない、表示が隠れる等。P3=完了を妨げない文言/見た目。機種/build/再現手順/期待/実際/匿名証拠をtemplates/DEVICE_CHECK.mdへ記入。Codexが修正→失敗した手順と関連回帰を再検査→人が実機確認。基準を結果に合わせて緩めない。
