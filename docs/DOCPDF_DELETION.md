# docPDF 写真の削除・取り消し

2026-10-08 / 保存専門担当の設計・合成検査。実ブラウザーのIndexedDB・実機は別途検証する。

## 利用者への意味

撮影した写真と写真から取り込んだ文書を同じPageとして扱う。「ごみ箱へ移す」は一覧と新しいPDFの選択から除外し、原本・編集版は端末内に保持する。ごみ箱から戻せる。端末から消去したとは表示しない。

「完全に削除」は対象名・1枚・取り消せないことを確認後、ごみ箱の写真のPage、全Revision、共有されていない原本／編集AssetをIndexedDBから削除する。ブラウザー／ストレージ装置の物理領域の安全消去を保証する操作ではない。メール、端末へ保存したPDF、外部ZIP、写真アプリの元画像には影響しない。

完成PDFの元になった写真は完全削除を止める。現行の復元ZIPはPDF→ページの参照が揃うことを必須としているため、原本を消しながら同じ形式を保証できない。ごみ箱への移動はでき、完成PDFのバイト・履歴・共有は保持する。今後その制限をなくすには、削除済みの参照を保持できる新しいバックアップ契約と移行検査が必要。

## APIと整合性

`src/storage/deletion.ts` の `movePageToTrash(id, true, token)`、`restorePage(id, token)`、`permanentlyDeletePage(id, true, token)` はトランザクション完了後だけ結果を返す。確認フラグはUIの確認を要求するための契約であり、セキュリティ境界ではない。対象がすでに削除された場合、削除の再実行は変更なしで成功し、復元はエラー。

既存の単一書込みリース／世代トークンで全操作を防護し、同じ短いreadwriteトランザクション内でPage、Revision、PdfExport、Jobを再取得する。画像のデコード、ハッシュ、外部通信、全AssetのBlob読込みはトランザクション内に置かない。古いトークン、Quota、abortは既存データを残し、成功表示を禁止する。RUNNING／VERIFYINGのPDFに使われている写真は処理が終わるまで削除しない。

原本と編集Assetは他Page、他Revision、完成PDFから参照がある場合に残す。他Pageが対象のRevisionを直接参照する破損は削除を停止する。自動削除・日付丸ごとの削除・DB初期化はしない。

現行DBには独立したサムネイルAssetはなく、表示用Object URLを画面側で破棄する。将来サムネイルを永続化する場合はその参照も同じ原子操作に追加する。ページIDを持たない旧PDFでRevisionの参照が欠ける場合は、対象との関係を判定できないため完全削除を止める。

## 画面・PDF・復元への接続条件

- 通常一覧、新規PDF選択は`!page.deletedAt`のみ。ごみ箱では`deletedAt`ありを表示し、戻す操作と明示した完全削除を分ける。
- 編集保存はコミット時にPageが存在しており`deletedAt`がないことを再確認する。古い編集画面からごみ箱を復活させない。
- PDF作成はトランザクションで現行Pageの存在、日付、deletedAtなし、選択Revision一致を検証してからJobを追加する。PDF作成中の削除はAPI側でも止める。
- 復元ZIPはごみ箱の写真も含めることを利用者へ示す。PackedPageへ任意`deletedAt`を追加し、妥当な日時だけ受け付け、復元時も維持する。完成PDFとの参照を保つため、ごみ箱を黙って除外しない。旧アプリは任意フィールドを読まないため、旧版への復元では通常一覧へ戻る可能性を説明する。
- 写真がすべてごみ箱でも、完成PDFの表示とバックアップは利用できる。完全削除済みはバックアップに含まれない。

## 合成検査と残る検証

`tests/deletion.test.ts` は確認・ごみ箱／復元・反復削除・旧PDF参照・共有Asset・PDF処理中・世代競合・合成要求キューでのabort／Quota・PDFバイト保持を検査する。実IndexedDBの実装を代替する合格証拠ではない。実ブラウザーで削除直後の再起動、途中閉じる、Quota、複数タブ、ZIP書出し→復元のごみ箱保持、PDF共有継続を確認する。
