# IMAGE_PDF_SHARE｜細字を残す加工と添付
版 2.0 / 画質値・処理時間は受入目標であり未計測

## 1. 編集契約
受取原本 → EXIF向きの一度だけの正規化 → 4点透視補正 → 利用者の90度回転 → 色調補正 → 確定JPEG/PNG → PDF。
四隅は正規化した「回転前の全画角マスター」に対する0..1座標。順序は左上・右上・右下・左下。画面回転/ズームに合わせた逆変換を単体試験。交差、ゼロ面積、範囲外を保存しない。EXIFによるブラウザーの自動回転と自前処理を二重適用しない。
プレビューの作業解像度と保存解像度を分離。確定保存は原本/全画角マスターからやり直し、加工済み画像の再圧縮を繰り返さない。切り抜きをやり直すときも全画角に戻れる。ただしOSから受け取らなかった範囲を復元する機能ではない。

## 2. 白黒の意味
標準は「読みやすい白黒（階調あり）」: 背景を控えめに明るくし、文字の濃淡を残す。グレースケールは階調を保つ。カラーは印影・薄字を残す退避経路。強い二値化は利用者が選ぶ独立モードにする。
小数点や薄い鉛筆を消した状態で、白く見えるだけの成功と評価しない。入力で読み取れる文字・細線が変換後に欠落するなら標準フィルターを弱める/修正する。比較表示と原本へ戻す操作を常に残す。
生成AIによる文字の補完、生成的超解像、OCR結果での字の置換、署名/印影/汚れの自動消去は使わない。撮影前のピンぼけを読める文字へ生成する機能ではない。

## 3. 手動と自動の順序
まず手動四隅＋透視補正を安定させる。四隅操作は拡大ルーペ、ドラッグ以外の微調整、取り消しを検討。UIの小さなつまみを大きい指で合わせられるか試験する。
自動検出は低解像度画像で候補を求め、原本座標へ戻して利用者へ提示する。低信頼・複数候補・白い机・影・用紙欠けでは手動へ。自動確定・自動撮影・文字領域の欠落を許さない。
候補アルゴリズムはOpenCVの輪郭/多角形近似等。採用判定は同じ試験紙で手動の所要時間・修正回数・切り落としを比較する。使いにくい自動処理は初版では無効にしてよい。R03は元要望どおり、自動より正確な手動を優先する。[W13-W15]

## 4. 解像度と容量
A4全面で300ppi相当なら、210/25.4*300 ≒ 2480、297/25.4*300 ≒ 3508画素。これは換算目標であって、レンズ・ピント・手ぶれの保証ではない。足りない画素を引き伸ばして「300dpi画質達成」と言わない。
この大きさのRGBA1枚は約33.2MiB。コピーやOpenCV内部配列が重なるとさらに増える。全ページ同時展開禁止。出力は原本の有効解像度を上限にし、8.7MP前後を品質基準の例として比較する。
初期エンコード候補はJPEG quality=0.92、グレー/二値でPNGが適するケースを比較。値は各ブラウザーの同等画質を保証しない。品質を下げるモードは別設定にし、利用者選択と実効画素数を記録。標準の最終値は実機比較で決定する。
強い影や複写紙も試験する。色/階調変化は目視で読めるかを優先し、画素一致率だけで品質を断定しない。

## 5. PDF生成
最初に選択したrevisionId、順序、紙サイズ、品質設定、表示名をスナップショット化。0枚は不可、同じボタンの連打で多重ジョブを作らない。
画像を1ページずつ読み、pdf-libでJPEG/PNGを埋め込む。A4は画像全体が収まるfit、または画像縦横比のページ。横縦混在を許可し、端を勝手に切らない。JPEG埋込みを利用してもメモリ使用量が一定と仮定しない。[W18]
ジョブ: QUEUED → RUNNING → VERIFYING → READY。割込みはINTERRUPTED/FAILED/CANCELED。READY前のPDFは共有不可。
生成後にPDFを再読込みし、ページ数・サイズ・構造・必要ページの描画を検査。PDF BlobとREADYを同一DBコミットで保存。実行時の軽い検査と配布前の全ページ比較を分ける。
スマホでは完成PDFの現在ページだけを描画する。画像サムネイル一覧を「生成済みPDFが正しく開けた証拠」としない。別のPDFビューアで開く検証も行う。

初版認証は10ページ。20ページを試して全対象で安定するなら上限20へ。1PDFを小さく分割する案内を持つ。10MiB超で容量注意を出すのはアプリ独自の初期案であり、メールの共通制限ではない。メールサービス上限はサービスごとに異なるため決め打ちしない。

## 6. 共有の重要な実装条件
W3CのWeb Share APIはセキュアなコンテキストとユーザー操作を要求する。`canShare({files:[pdfFile]})`で実際のFileを検査する。`navigator.share`があるだけでPDF添付対応済みと判定しない。[W10]
**PDF生成と共有を1回の長い非同期クリック処理にしない。** PDFを先に完成・保存し、共有可能なFileを画面側に準備してから「共有して送る」を有効にする。そのクリック内で、PDF生成・DB取得・通信のawaitを挟む前に`navigator.share({files:[pdfFile]})`を呼ぶ。
filename変更時には共有用Fileも作り直す。Object URL文字列をPDF添付の代わりに共有しない。メールアプリを決め打ちしない。宛先指定をWeb Shareで必ず渡せるとは約束しない。
共有の成功Promiseは実メール送信・相手への到達ではない。ShareEventは「共有を要求」「OSへの引渡し結果」「取消/失敗」まで。送信済み表示を用意するなら利用者の自己申告と明記する。
AbortErrorをデータ保存失敗と表示しない。非対応・共有先なし・NotAllowedErrorなどは、既存PDFを保持して別経路を案内する。共有後も保存済みPDFを自動削除しない。

## 7. 救済経路と合格線
直接共有が使えない場合は、PDFを「ファイルに保存/ダウンロード」→ OSのファイル画面から共有、またはメール側で添付。`mailto:`には添付を保証する標準機能がない前提で、主経路にしない。
初版の対象iPhone/Androidでは、実機でPDFを直接共有し、メールの添付と受信側のページ/名前/表示まで確認してH01合格とする。ファイル保存だけの成功で「メールまで一貫対応」と宣伝しない。
直接共有の重大問題が解消しないなら、無償条件のまま救済動線を採用してよいかを監督へ判断カードで示す。未承認でR07を縮小しない。機種/OS/メールアプリごとに既知制限を記録する。
