# ARCHITECTURE｜無料・両OSの構成
版 2.0 / 具体的なパッケージ版はM0で確認し固定する

## 1. 全体
利用者のiPhone / Android
  → React画面（PWA）
  → 撮影/画像取込アダプター
  → IndexedDBの下書き保存
  → Web Workerの画像処理
  → IndexedDBの画像版・PDF保存
  → Web Share API / ファイル保存

Cloudflare PagesはHTML・JS・WASMなど**アプリのプログラム**だけを配信する。文書画像やPDFをアップロードするAPIは作らない。Pagesへの通常アクセスにはIPアドレス等の通信情報が生じるため、「通信が一切発生しない」とは言わない。
GitHubはコード・匿名試験素材・仕様の管理。利用者の文書の保存先ではない。

## 2. 技術表
| 層 | 採用方針 | 根拠・注意 |
|---|---|---|
| UI | TypeScript + React + Viteの静的SPA | サーバー描画・Next.js・ログイン基盤を目的なく導入しない [W21] |
| PWA | vite-plugin-pwa / WorkboxのinjectManifestを第一候補 | 手動更新・資源キャッシュを制御。設定は版と公式仕様で照合 [W19] |
| 撮影 | `<input type="file" accept="image/*" capture="environment">` | OSの撮影/選択UIを呼ぶ。背面カメラ指定はヒントであり機種統一UIではない [W11] |
| 画像取込 | captureなしの別ファイル入力 | JPEG/PNGが基準。iPhoneのHEICは実際のデコード経路を検査 [W12] |
| 編集 | OpenCV.js（単一スレッドWASM）+ Canvasの座標UI | 射影・色調処理を分離。JS/WASMはビルドへ同梱、外部CDNに実行時依存しない [W13-W15] |
| 保存 | IndexedDB + Dexie.js（ローカル機能のみ） | Blobとメタデータを同一DB内で管理。Dexie Cloud・同期は使わない [W16-W17] |
| PDF | pdf-libによるJPEG/PNG埋込み | `save()`時の全体メモリに注意。完全ストリーミングとは説明しない [W18] |
| PDF表示 | 確定PDFをPDF.js等で必要ページだけ描画する候補 | ライブラリはM0で保守/サイズ/ライセンス確認。原画像一覧だけをPDF検証の代用にしない |
| バックアップ | ZIP + JSON manifest + SHA-256 | 無料の保守されたZIP実装をM0で評価。コード発明・全量巨大展開を避ける |
| 自動検査 | 型検査、単体テスト、Playwright Chromium/WebKit | 実iPhoneのカメラ・メール・保存は別試験 [W20] |
| 配布 | Cloudflare Pages Freeの静的配信、固定pages.dev URL | Functions / R2 / KV / 有料ストレージなし [W03-W07] |

外部パッケージは依存ツリーとライセンスを監査する。バージョン、ダウンロード元、ビルド用Node、ブラウザー版、WASMハッシュをENVIRONMENT_LOCKに記録。latestを恒久的なビルド指定にしない。PDF.jsやZIP実装等は候補であり、未監査の推奨版を捏造しない。

## 3. モジュール境界
- `capture/`: OSファイル取得、取消、保存先の日付保持。DOM入力の参照を画像の永続保存と扱わない。
- `storage/`: トランザクション、保存成功表示、復旧、容量、単一編集セッション。
- `editor/`: ズーム・四隅・回転・比較UI。低解像プレビューだけを担当。
- `processing/`: 正規化、透視補正、階調、確定画像出力。workerとメインスレッドの契約を固定。
- `exports/`: 版・順番固定、PDFジョブ、容量表示、実PDFプレビュー。
- `share/`: File準備、能力検査、直接共有、ファイル保存、結果の正確な表現。
- `backup/`: 日付単位のexport/import、形式検査、ハッシュ、既存データとの分離。
- `update/`: Service Worker更新待機、複数画面協調、DB互換性、復旧モード。

## 4. 対応環境
初版のiPhone基準はiOS 17以降を暫定下限とする。これはSafari 17のStorage API/HEICの公式情報を踏まえた設計値で、当該版全機種の実機合格を意味しない。[W08, W12]
M0でその時点の最新安定OS/ブラウザーと、利用予定の少なくとも1台のiPhone（可能なら低メモリ機も）を記録。Androidは利用予定の端末の型番・OS・ブラウザーをM0で記録する。未確認のOS版を決め打ちしない。
通常利用はiPhone Safariから追加したホーム画面版、Android Chromeのホーム画面版。通常タブも確認対象。アプリ内ブラウザーや埋込みiframeを標準動線にしない。プライベートブラウズでの長期保存は非対応と説明するが、プライベート状態を確実に検出できるとは仮定しない。

## 5. 撮影と互換性
まずOSの写真撮影UIから戻る1枚単位の経路を実装する。カメラアプリ内で撮影中にOSが終了した未受取写真は保護できない。すでに確定保存した別ページを巻き込まない。
getUserMediaのライブカメラ、ImageCapture、リアルタイム自動シャッターは初版必須にしない。動画フレームの切出しを高精細静止画の代替として黙って採用しない。
OSがFileとして渡す時点で変換・メタデータ変更がある場合がある。保存するのは「受け取った写真の原本」であり、センサーのRAWやOSが渡さないオリジナルまで保持すると説明しない。
HEICはブラウザーによるネイティブデコードを先に試す。未対応の場合は明示してJPEG等の再選択/再撮影を案内。顧客画像を外部変換サービスへ送らない。HEICの表示対応がCanvas/Workerの全経路を保証すると仮定しない。

## 6. リソースとオフライン
画像処理は1ジョブ1ページ、展開ピクセルを同時に大量保持しない。Workerだからメモリ無制限、とは扱わない。cv.Matはfinallyで解放、ImageBitmap/Object URL/Canvasも用途終了時に解放する。[W15]
UI用画像は小さくするが、確定処理は保存原本から作る。巨大な24MP/48MP等の入力は安全上限を調査し、原本を残して処理上限を説明する。無断縮小による見かけの成功は禁止。低精細版を選ぶ場合も利用者の選択を記録。
単一スレッドWASMを初期構成とし、SharedArrayBuffer/クロスオリジン分離/複雑な並列GPU構成を必須にしない。入力と出力のピクセル寸法から展開メモリを見積もり、実機で検証する。
WASM・worker・PDF表示・バックアップを含む初版必須資源を同一オリジンに固定しキャッシュする。PWAツールのサイズ上限によるWASMキャッシュ除外を検査し、オフラインで1枚処理が通るまで「準備完了」にしない。
オフラインで撮影・加工・保存・PDF生成が動くことを目標とする。メールの配送、初回準備、更新取得にはネットワークが必要。
