# RELEASE_AND_COST｜基本無料・更新・公開境界
版 2.0 / 2026-10-02確認 / 公開やサービス接続は未実施

## 1. 基本無料の定義
本アプリの利用料、文書の加工/PDF生成、静的なアプリ配信について追加の月額運用費0円を目指す。サーバー側で画像を変換せず、生成AI API、有料スキャンSDK、アカウント基盤、クラウド保存を初版に入れない。
開発者のCodex/ChatGPT契約・追加クレジット、通信料、端末代、保守の時間は含まない。利用者は本アプリのためにCodexを契約しない。無料枠の条件は将来変わり得るため永久0円を保証しない。

| 項目 | v2の方針 | 課金防止 |
|---|---|---|
| アプリ配布 | Cloudflare Pages Freeで静的ファイルのみ | Functions / R2 / KV / D1 / Workersの動的APIを作らない |
| 公開URL | 無料のpages.devを固定 | 独自ドメイン購入を前提にしない |
| ストア | 初版は不使用 | Apple/Google開発者登録を要求しない |
| 文書保存 | 利用者のブラウザー内＋本人が外部保存 | サーバー保管・自動クラウド同期を付けない |
| 開発 | 既存Codex環境で、利用可能枠を確認 | 有料モデルAPIキーや追加クレジットを無断購入しない |
| 自動検査 | ローカル/既存Codexを先に使う | GitHub Actions等はアカウント無料枠を確認後に限定 |

公式資料では静的アセットのリクエストは無料かつ無制限とされる一方、Freeのビルドは月500回、同時1件、配信する単一アセットは25MiBまで等の制約がある。[W03-W04]
25MiBはホストするJS/WASMなどの1ファイルの上限であり、利用者の端末で生成するPDF容量の上限ではない。WASMを超大化してR2を追加するのではなく、必要モジュールや配信資源のサイズをまず減らす。
無料枠不足時はビルド頻度を下げる・変更をまとめる・不要なプレビューを減らす。課金移行は自動化しない。利用規約、無料枠、課金設定をM0/初回公開/変更時に再確認する。

## 2. 公開と更新の流れ
開発ブランチ → 自動検査 → 読取りレビュー → 非公開コードへのDraft PR → 承認済みの検証公開 → 実機試験 → かっしーの公開承認 → 本番へ反映。
GitHub連携はビルドとプレビューURLの生成を支援するが、**非公開リポジトリだから配信サイトも非公開とは限らない**。プレビューは初期状態では公開URLになり得る。外部へ置く前に明示承認を取り、サンプルは完全架空データのみ。[W05, W07]
初回のみ「検証用プレビューをこのサイトに出してよいか」を確認し、許可の範囲（指定リポジトリ/ブランチ、架空データ、料金0円、期限）をDECISIONSへ記録。その後の同範囲の再配信は都度同じ質問をしない。本番公開とプレビュー許可は別。
mainへのマージが自動本番反映になる設定では、マージ自体を公開操作として扱う。本番承認前にCodexがマージしない。今回はサービス作成・接続・配信を行っていない。

## 3. Service Worker更新
固定した同一オリジンのHTML・JS・WASMを更新する。利用者には作業終了後に「更新があります」を提示する。すべての利用者への即時・無操作反映ではない。
無条件のskipWaiting、autoUpdate、controllerchange直後の強制reloadを避ける。初期設定はprompt型。撮影、編集中、PDF生成中、バックアップ中は適用しない。[W19]
更新前に未保存の編集レシピをコミットし、実行ジョブがなく、他タブも書込みしていないことを確認。更新待機中は旧資源で作業を継続。新しい必須資源の事前取得に失敗したら旧版を維持。
更新確認は起動/フォアグラウンド復帰/手動確認を基本にする。無駄な秒単位の定期照会はしない。別バージョンのコードとworkerが混ざるケース、古いタブと新しいDBの併存を試験する。

## 4. DB変更とロールバック
初版からdataFormatVersion/minReaderVersionを持つ。可能な限り追加的なスキーマ変更を優先し、破壊的移行・`deleteDatabase`による初期化・全Cacheの無差別削除を禁止する。
移行は短いトランザクションで行えるものと、再開可能な段階移行を分ける。失敗時は旧データを残し、読取り/外部保存/修復版の経路を用意する。スキーマ更新前に外部バックアップを案内する。
Cloudflareのホスト側ロールバックは以前の配信版へ戻す機能。利用者端末のDBや、すでに有効なService Workerが即座に巻き戻る機能ではない。[W06]
そのため「アプリ資源を戻す」「データ互換性を保つ」「修正版を配る」を分ける。旧版が新データを読めないときは初期化せず、書込み停止と復旧案内。すでに配布したデータ形式は安易に後方非互換にしない。

## 5. 固定URLとアプリの同一性
配布前にorigin、manifest id、start_url、scopeを確定する。初版は1つのpages.devドメインを継続利用。プレビュー/本番/後日の独自ドメインは別保存領域として扱い、URL変更だけで既存文書が移行すると説明しない。
ホーム画面への追加前後のデータ共有も仮定しない。最初に正式なホーム画面版へ誘導。変更が必要なら旧URLから復元用ZIPを出し新URLで取込む。

## 6. セキュリティと文書
画像・本文・宛先・実ファイル名・EXIF・認証情報をログやAI入力、リポジトリ、CIへ送らない。診断は匿名ID、エラーコード、バイト数、時間、OS/ブラウザーの必要な範囲だけ。
ランタイムは同一オリジン資源のみを原則とし、外部解析タグ・広告・外部フォント・トラッキングSDKを入れない。CSP、frame-ancestors、Permissions-Policy、X-Content-Type-Options、Referrer-Policyは必要機能と実測に合わせる。WASM/workerを動かすために無条件の危険なワイルドカードへ緩めない。
アプリのコード更新は端末内文書へアクセスできるコードの変更でもある。サーバーを持たないことだけで安全と判定しない。依存ロック、改ざんの検査、CSP、公開権限、更新差分のレビューを守る。
データはOS/ブラウザーの保護に依存。アプリ独自の暗号化や暗号化バックアップを未実装のまま宣伝しない。共有先がメール/クラウド等なら利用者の選択でその先に送られる。

## 7. 終了・縮小
無料枠の変更、保守困難、重大な実機問題が発生したら、無断有料化より、更新頻度の縮小/新規配布停止/外部保存専用モードを優先する。読めるPDFと復元用ZIPを利用者が取り出せる移行期間を設計する。
